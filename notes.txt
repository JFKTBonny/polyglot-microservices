#################################
######### MICROSERVICES #########
#################################

Fundamental Concepts
********************
    * microservices is an architectural style where an application is built as a collection of small,independently deployable services,
      each running its own process and communicating via APIs...
    * Monolith vs Microservices: Microservices offer scalability and flexibility but introduce distributed system complexity...
    * Single Responsability Principles: Each service should own one business capability( e.g user service, order service...ect)

Service Communication
*********************
     * Synchronous: REST (HTTP/HTTPS), gRPC [ Client wait for response...]
     * Asynchronous: Message brokers like "" Kafka, RabbitMQ, AWS SQS ""...[ services communicate via events/messages without waiting...] 
     * API Gateway: A single entry point that routes requests to the appropriate service, handles auth, rate limiting, and load balancing...

Data Management
***************
     * Database per service: Each microservice owns its data store[- no shared databases]...
         This ensures loose coupling...
     * Event Sourcing: Storing state changes as a sequence of events rather than current state...
     * CQRS(Command Query Responsability Segregation): Separating read and write operations for scalability...
     * Saga Pattern: Managing distributed transactions across services(choreography vs orchestration)...

Resilience & Fault Tolerance
****************************
     * Circuit Breaker: Stop cascading failures by "opening" when a service is unhealthy...
     * Retry & Timeout: Handling transient failures gracefully...
     * Bulkhead Pattern: Isolating failures so one service does not take down others...
     * Graceful Degradation: Serving partial functionality when a dependency fails...

Service Discovery & Load balancing
**********************************
     * Client-side discovery: Service queries a registry itself...
     * Server-side discovery: Load balancer queries the registry ( e.g ,AWS ALB, KUBERNETES service)
     * Service Mesh: Infrastructure layer for service-to-service communication(e.g Istio, Linkerd)...

Containerization & orchestration
********************************
     * Docker: Packaging each service into a container  for consistency across environments...
     * Kubernetes(K8s): orchestrating containers...[ deployments, scaling, self-healing, networking...]
     * Helm: Package manager for Kubernetes applications...

CI/CD & DevOps
**************
     * Independent deployability: Each service should be deployable without affection others...
     * Blue/Green & Canary Deployments: Zero-downtime deployment strategies...
     * Infrastructure as code (Iac): Terraform, Ansible for reproducible environments...

Observability(The Three Pillars)
********************************
     * Logging: Centralized, structured logs (ELK Stack, Loki)...
     * Metrics: Performance data (Prometheus + Grafana)...
     * Distributed Tracing: Tracking a request across services( Jaeger, Zipkin, OpenTelemetry)...
     * Correlation IDs: Tagging requests with a unique ID to trace them across services..

Security
********
     * Auth patterns: OAuth2, OpenID Connect, JWT tokens passed between services...
     * mTLS (Mutual TLS): Encrypting and authenticating service-to-service traffic
     * Zero Trust: Never assume a service inside a network is safe...always verify..
     * Secrets Management: Vault, AWS Secrets Manager for sensitive config.

Organizational Considerations
*****************************
     * Conway's Law: Your architecture will mirror your team structure...[ design teams around services...]
     * Domain-Driven Design(DDD): Use Bounded Contexts to define service boundaries correctly...
     * Team ownership: Each team fully owns their service( buils, deploy,operate)...
